This extends the shared `commit` skill (in the user-level skills, `~/.agents/skills/commit`) with three mandatory reviews: documentation drift, per-user data isolation, and logging coverage. Follow the shared skill's steps; at its review step, run the three reviews below, and do not commit while any of them finds a gap.

Also never stage `apps/mobile/android/` (generated by Capacitor) or `apps/web/dist/`; if one appears in the diff, fix `.gitignore` instead.

## Documentation review

Mandatory and exhaustive: for every change, open the docs that describe the touched area and reconcile them, whether or not the change feels user-visible. Check each surface:

- `README.md`: features, platforms, the Developers links and the licence.
- `ARCHITECTURE.md`: the parts, the persistence and sync models, and "Where data lives" whenever the product starts or stops writing somewhere.
- `docs/development.md` and `docs/deployment.md`: commands, setup, releases, server config, backup, export and deletion.
- `apps/mobile/README.md`: Android build, run, signing and the native plugin flow.
- Every tracked `AGENTS.md` (list them with `git ls-files '*AGENTS.md'`) and `.agents/guides/`: conventions, helper inventories and invariants.
- The `docs/` contracts: `auth-architecture.md`, `data-event-contract.md`, `alarm-architecture.md`, `notification-behavior.md` and `desktop-architecture.md`, whenever auth, the HTTP and WebSocket data flow, the alarm and escalation mechanism, the user-facing done, silence and snooze guarantee, or the Windows tray app changed. The guarantee and the mechanism are separate documents because a change can move one without the other.
- `.agents/skills/`: when a workflow, script or expectation changed.
- `.env.dev.example` and `.env.server.example`: when an environment variable or config key changed.
- Build and deploy descriptors: `Dockerfile`, `compose.server.yml`, `nginx.server.conf`, `.github/workflows/*` and the package scripts.
- In-code docs: the JSDoc header of each non-trivial module changed (it must still name what the module owns and its invariants), and any comment the change made untrue.

## Data-isolation review

- Read `apps/api/AGENTS.md` and `docs/auth-architecture.md` for the model and its exceptions (sharing, assignment, administrator counts).
- Every changed domain query is scoped to the authenticated user (`requireUserId(request)`), or proves the explicit share or assignment grant the model allows.
- Edit and delete paths re-fetch ownership rather than trusting an id from the path.
- New request bodies are validated at the boundary with a Zod schema from `@persistent/shared`.

## Logging-coverage review

Operational logs go through `apps/api/src/lib/logger.ts`.

- New or changed failure paths are observable through `logger.warn` or `logger.error`. An empty `catch {}` or `.catch(() => ...)` that drops a real error (scheduler loops, push delivery, email, the WebSocket hub) is a gap; keep a swallow only when it is genuinely benign, and say why in a comment.
- Levels fit: failures at `warn` or `error`, not `info`, and no per-iteration logging in the scheduler's tick and sweep hot paths.
- Nothing secret is logged: no session secrets, sign-in or email codes, FCM tokens, or raw request bodies. Log error messages and safe identifiers only (userId, reminderId, occurrenceId, status codes).

Report: on top of the shared skill's report, which documentation surfaces you reviewed and which you updated (say so when a surface needed no change), and the result of the data-isolation and logging reviews.
