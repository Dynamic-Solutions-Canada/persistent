# Host bridge contract

This file owns the boundary between the hosted web page (`apps/web`) and the three native hosts that load it: the Windows WinUI 3 tray app with WebView2 (`apps/desktop`), the Linux Electron tray app (`apps/linux-desktop`) and the Android Capacitor app (`apps/mobile`). It lists every message, method, event and fallback that crosses that boundary today, in both directions, and how each side copes with an older or newer counterpart. It is the source of truth for the bridge itself; the behaviour behind each message (alarms, notifications, sessions, localization) stays in the documents linked below. The hosted page updates the moment the server deploys, while installed hosts update slowly or never, so every rule here is written for version skew.

Related documents, linked rather than restated: [desktop architecture](desktop-architecture.md) (Windows process model, settings, notifications, widget), [Linux desktop architecture](linux-desktop-architecture.md) (Linux process model, authentication and IPC), [alarm architecture](alarm-architecture.md) (Android alarm plugin, appearance, Back, permissions), [localization](localization.md) (the `NativeLocale` and `NativeLanguageState` payloads), [auth architecture](auth-architecture.md) (passkeys, Google sign-in, sessions, export) and [data and event contract](data-event-contract.md) (`/ws`, sync and the device-alarm projection).

## Hosts at a glance

| Host                | Page detects it with                                                                     | Platform id the page reports            | Transport                                                                                             | Page-side module                                      |
| ------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Windows (WebView2)  | `window.chrome.webview` with a `postMessage` function, and no `window.persistentDesktop` | `desktopPlatform()` returns `'windows'` | `chrome.webview.postMessage` (page to host), `CoreWebView2.PostWebMessageAsJson` (host to page)       | `apps/web/src/native/desktopBridge.ts`                |
| Linux (Electron)    | `window.persistentDesktop` (exposed by the preload) with `platform: 'linux'`             | `desktopPlatform()` returns `'linux'`   | `persistentDesktop.postMessage` over IPC channel `persistent:host`; host replies on `persistent:page` | `apps/web/src/native/desktopBridge.ts`                |
| Android (Capacitor) | `Capacitor.isNativePlatform()` through `isNative()`                                      | `classifyClient` reports `android`      | Capacitor plugin calls and plugin events                                                              | `apps/web/src/native/alarmBridge.ts`, `nativeSync.ts` |

Detection rules (`desktopBridge.ts`, `alarmBridge.ts`):

- `desktopTransport()` returns `window.persistentDesktop ?? window.chrome?.webview`. `isDesktopHost()` is true when that transport has a `postMessage` function. `desktopPlatform()` returns `'linux'` only when `window.persistentDesktop.platform === 'linux'`, otherwise `'windows'`, so every existing WebView2 build stays Windows without sending anything.
- `isNative()` (Capacitor) and `isDesktopHost()` are independent. Capacitor is absent in both desktop hosts, so `isNative()` is false there; neither desktop transport exists in Android. Code must not treat one as the other.
- `hasNativeUpdater()` is `isNative() && Capacitor.isPluginAvailable('Update')`, which is true only in the `direct` Android flavor.
- Session metadata (`apps/web/src/native/clientUsage.ts`) reports `{ app, platform }` as `android`/`android`, `windows`/`windows` or `linux`/`linux` from these checks, before falling back to the user agent for browsers and PWAs.

## Desktop channel (Windows and Linux)

Both desktop hosts speak one message protocol, defined page-side by `desktopBridge.ts`. Every message is a JSON object with a string `type`. Payload shapes that are shared with the hosts live in `packages/shared/src/desktop-host.ts` (`DesktopHostSettings`, `DesktopHostSettingsPatch`, `DesktopWindowSize`, `DesktopSnoozeChoice`) and `packages/shared/src/locales.ts` (`NativeLocale`). The widget snapshot shape (`WidgetSnapshot`) is defined in `desktopBridge.ts` and mirrored in C# by `apps/desktop/Shared/WidgetSnapshot.cs`.

### Delivery rules

- **The page never trusts a host message.** `onHostMessage()` (`desktopBridge.ts`) ignores non-objects and unknown types, validates `navigate.path` (must start with `/`, not `//`, and contain no backslash, control or space characters), bounds `snoozeOccurrence.occurrenceId` to 1 to 512 characters, and runs `hostSettings.settings` through `parseHostSettings`, dropping the message when that returns null.
- **Every subscriber handles host messages with an explicit check and does nothing for anything else.** A fall-through once turned `checkForUpdate` into a Back press that closed the flyout on every open; see `useNativeBack.ts` and the light-dismiss section of [desktop architecture](desktop-architecture.md).
- **Page posts are fire and forget.** `postToHost()` is a no-op outside a desktop host and swallows transport exceptions; every caller copes with no reply.
- **Hosts buffer page-directed intents until the page says it is listening.** The page posts `pageReady` once its routing subscription is attached (`useNativeBack.ts`). Windows holds the latest `navigate` path and a pending widget refresh until then (`AppFlyout.NavigateTo`, `_pageListening`, `apps/desktop/Persistent.Desktop/Windows/AppFlyout.xaml.cs`). Linux holds the latest `navigate` or `snoozeOccurrence` in `PageDelivery` (`apps/linux-desktop/src/page-delivery.ts`); `snoozeOccurrence` additionally waits for `notificationActionsReady`. Linux resets readiness on every new main-document navigation and keeps it across same-document (SPA) navigations. Windows resets it only when the host itself navigates to the app (`NavigateToApp`), not when the page reloads itself (see Known gaps). Only the latest pending intent is kept.
- **Messages not covered by buffering** (`back`, `checkForUpdate`, `hostSettings`) are posted directly and lost if no listener is attached; each is either user-initiated against a visible page or repeated later.

### Topic notes

- **Locale and time format.** The page sends `locale` only after native language reconciliation is ready, whether or not the user is signed in. Windows contributes `deviceTimeFormat`; `useSettings.tsx` uses it for Match device when no explicit clock is saved, falling back to the regional locale on Linux and older Windows hosts. See [localization](localization.md).
- **Appearance.** Only the resolved `mode` and the selected palette's `background` cross the desktop channel. Initial chrome follows the OS until the page loads.
- **Notifications and the alarm projection.** No desktop message carries reminder or alarm data. Each desktop host runs its own `/ws` connection and reads `/api/sync/occurrences?alarmsOnly=true` with the session cookie it borrows from its own browser profile, so the page's only role in notifications is `signedIn`, `signedOut`, the `notifications` host setting and (Linux) the snooze picker. The hosted page never requests browser notification permission. See the notifications sections of [desktop architecture](desktop-architecture.md) and [Linux desktop architecture](linux-desktop-architecture.md).
- **Sync.** Desktop hosts have no page-driven sync. `checkForUpdate` is the only resume signal the page receives.
- **Updates.** Host updates are owned natively (Windows: About page and the Store; Linux: the update controller in its settings window) and never cross the bridge. `checkForUpdate` refers to the hosted web build only.
- **Version reporting.** Neither desktop host tells the page its version. `collectClientUsage` reads a native version only for Android, so desktop sessions report `nativeVersion: null`.
- **Sign-in and session.** Credentials never cross the desktop bridge. Windows reads the cookie from the WebView2 profile per call (`AppFlyout.GetSessionCookieAsync`); Linux reads the HttpOnly `persistent_auth` cookie from its Electron profile per call and watches it for account changes (`apps/linux-desktop/src/profile-session.ts`). A cookie identity change on Linux pauses delivery and discards pending intents even without a `signedOut` message.
- **Passkeys.** On both desktop hosts `isNative()` is false, so `passkeyClient.ts` calls the browser WebAuthn API through `@simplewebauthn/browser`; no bridge message is involved. Windows Hello through WebView2 is described in [desktop architecture](desktop-architecture.md). On Linux the hosted profile denies every permission request and check, and the Linux verification record lists real authenticator login as not yet checked, so whether passkeys work there is unverified.
- **Account export.** `AccountExportSection.tsx` offers a `target="_blank"` link to `/settings` on Windows (which the host sends to the default browser) and instructions on Linux and Android.

## Android channel (Capacitor)

The Android app loads the hosted page from `server.url` in `apps/mobile/capacitor.config.ts` (production `https://persistent.dynamic-solutions.ca`, or a loopback dev URL). Custom plugins are registered in `apps/mobile/android-plugin/MainActivity.java`: `AlarmPlugin`, `Passkey`, `GoogleAuth`, plus `Update` in the `direct` flavor only (`flavor/direct/FlavorPlugins.java`; the `play` flavor registers nothing). `@capacitor/app` and `@capacitor/push-notifications` register themselves. The page declares the custom plugin interfaces in `alarmBridge.ts`; no shared schema covers the method arguments except where noted.

### Other Android plugins and channels

- **`Update`** (direct flavor only): `downloadAndInstall({ url })` downloads an APK with `DownloadManager` and launches the installer. The page uses only the plugin's presence (`hasNativeUpdater()`) to show the direct-build migration notice (`DirectBuildMigrationNotice.tsx`, `AppUpdateInformation.tsx`); see "Legacy Android update compatibility" in [data and event contract](data-event-contract.md).
- **`Passkey`**: `createPasskey({ options })` and `getPasskey({ options })` take WebAuthn options as a JSON string and resolve `{ response }` as a JSON string, through Android Credential Manager, because the Android WebView has no `navigator.credentials`. `passkeyClient.ts` routes here when `isNative()`. See [auth architecture](auth-architecture.md).
- **`GoogleAuth`**: `signIn({ serverClientId })` resolves `{ idToken }` from Credential Manager; `GoogleSignInButton.tsx` posts it to the server. Android therefore uses no Google popup.
- **`App`** (`@capacitor/app`): `getInfo()` supplies the installed `versionName`, shown by `useAppVersion.ts` and reported as `nativeVersion` in session metadata; `exitApp()` leaves the app on exhausted Back. `NativeApp` in `alarmBridge.ts` is a minimal proxy of the same plugin.
- **`PushNotifications`**: `requestPermissions()` is the runtime notification prompt (`launchGrant.ts`), and `register()` runs only when `/api/push/config` reports `fcmEnabled`.
- **Safe-area insets**: `WebViewSystemInsets.kt` writes `--native-safe-area-inset-{left,top,right,bottom}` CSS properties on the document root with `evaluateJavascript` after layout and page loads. `apps/web/src/lib/safeArea.ts` uses the greater of these and `env(safe-area-inset-*)`.
- **Session cookie**: the page never reads the session cookie. Native code reads it only inside `setSyncConfig` and mirrors it for the background worker. See [alarm architecture](alarm-architecture.md).
- **External links**: no repository code customizes Android navigation or new windows, and `capacitor.config.ts` sets no `allowNavigation`, so Capacitor 6's default applies (`Bridge.launchIntent`): a URL on the app's own host and scheme loads inside the WebView, and any other host or scheme opens through `ACTION_VIEW`, usually the system browser. Multiple windows are off, so `target="_blank"` behaves the same way. A same-origin page the app wants in the system browser (the account export) therefore cannot reach it without native code.
- **Deep links**: the manifest additions declare no app-link or URL-scheme intent filters (only boot, FCM and, in the `direct` flavor, the Android Auto service). The only way into a page route from outside is a notification tap, carried as the `EXTRA_REMINDER_ID` intent extra and drained through `consumePendingNavigation`.

## Version skew and fallbacks

There is no bridge-level protocol version and no host version handshake. Compatibility rests on capability detection, additive optional fields, per-payload `version: 1` literals and receivers that ignore what they do not understand.

### An older host with a newer page

| Mechanism                                                                                                                                                                                                                                                                             | Where                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |

### A newer host with an older page

Desktop hosts can point at a self-hosted server whose page is older than the host, and a new host release can reach users before the matching page is deployed, so this direction is real.

- Windows ignores a `close` that arrives within 500 ms of the flyout opening (`AppFlyout.OnWebMessageReceived`), which breaks the loop a stale page once caused by treating `checkForUpdate` as Back.
- Windows and Linux hosts keep working when the page never sends `signedIn`: the window simply stays in sign-in mode ([desktop architecture](desktop-architecture.md) notes that the hosted bridge must ship before the host that depends on it). Linux delivery stays paused until `signedIn` or a cookie change resumes it.
- Hosts keep sending the required legacy `hostSettings` fields (Linux sends a fixed `snoozeMinutes` and one `snoozeChoices` entry for exactly this reason) so an older `parseHostSettings` still accepts the payload.
- Android keeps `requestOverlayPermission`, `ensureFullScreenIntent` and `requestBatteryExemption` for older bundles that do not call `openPermissionSettings`.
- `AlarmSpec.fromJson` defaults every field an older page might omit (`bodyTemplate`, `baseBody`, sound titles, `shadeProminence`). `setLocale` and `setAppearance` reject a payload whose `version` is not 1.
- Server-side, `syncAlarms()` tolerates an older server without `agenda` (`data.agenda ?? []`), and `SyncClient.kt` tolerates a missing `agenda` array.

### What is not additive

- `parseHostSettings` rejects the whole `hostSettings` payload when `platform` or `flyoutPlacement` carries a value it does not list, or when a required field is missing or mistyped. A new enum value or a removed required field therefore hides every desktop control on pages that predate it.
- The payload literals (`NativeLocale.version`, `NativeAppearance.version`, `NativeLanguageState.version`, `WidgetSnapshot.version`) are exact matches on both sides. Bumping one is a breaking change for every installed host or page that still checks for 1.
- `navigate` paths are interpreted by the page's router, so a route the older page does not have lands wherever that page sends unknown paths.

## Security boundaries already enforced

- **Inbound origin checks.** Windows acts on a page message only when `args.Source` matches the configured server's scheme, host and port (`IsAppUrl`). Linux accepts `persistent:host` only from the managed `webContents`, its main frame, and a frame URL on the configured origin.
- **Outbound origin check on Linux.** `HostedWindow.send()` posts to the page only while the view's URL is on the configured origin.
- **No page-callable IPC beyond the bounded bridge.** The Linux preload exposes only `platform`, `postMessage`, `addEventListener` and `removeEventListener` through `contextBridge`, never `ipcRenderer`, Node APIs or cookies, and only in the main frame. External links use a separate channel that only the isolated preload's trusted-click handler sends. Authentication popups get only `external-preload` (no host bridge). The local flyout chrome (`persistentChrome`, `shell-preload.ts`) and the packaged settings and audio windows (`persistentLocal`, `local-preload.ts`) have their own transports and never load hosted content.
- **Renderer isolation on Linux.** Every window uses context isolation, the sandbox and no Node integration; the hosted profile denies every permission request and check.
- **Trusted-click-only external links on Linux.** The page cannot open the system browser by script: only a trusted link click captured by the preload, or a local host action (the tray and toolbar "Open in browser"), reaches `shell.openExternal`, and only for `https:` or app-origin URLs without credentials. Redirects, script navigations and script popups to other origins are blocked.
- **Validation of every payload.** Windows: `HostSettings.ApplyAsync`, `FlyoutAppearance.TryRead`, `UiText.Apply` (persists only canonical fields), `WidgetSnapshotStorage.TryParse` (field length caps, at most four items, no items when signed out). Linux: `nativeLocaleSchema`, `HostSettings.apply`, the appearance regex. Android: `NativeText.save`, `AlarmAppearance.save`, `AlarmPermissions.Grant.fromKey`. Page: `onHostMessage` and `parseHostSettings`.
- **Credentials stay native.** No bridge message carries a cookie or token. Desktop hosts borrow the cookie from their own profile per call; Android reads it natively for the background worker.
- **Windows WebView2 settings.** Developer tools are disabled and web messaging is enabled; the default context menu stays on for cut, copy and paste.

## Changing this contract

- Any change to a message, method, event, payload field or fallback updates this file in the same commit, along with `packages/shared` when a shared type changes and the tests beside each side (`apps/web/src/native/desktopBridge.test.ts`, `apps/linux-desktop/src/page-delivery.test.ts`, `host-settings.test.ts`, `security.test.ts` and the relevant Android tests).
- Keep changes additive. Add new optional fields and new message types; do not rename, remove or retype existing ones, and do not add values to a field an older receiver validates as a closed set.
- Keep older hosts working. The hosted page updates for every user at the next deploy, while installed hosts update through the Microsoft Store, Google Play, GitHub APKs and AppImage downloads on the user's schedule. Every new page call must detect the capability (`UNIMPLEMENTED`, plugin presence, an optional field, or no reply) and degrade to today's behaviour.
- Ship the hosted side first when a host change depends on a new page message, and make the host tolerate a page that never sends it.
- Handle host messages with an explicit check and a do-nothing default, on both sides.
- Keep reminder, schedule and status rules out of the bridge: hosts receive display-ready data from the server projection or the widget snapshot, never a reason to reimplement those rules.

## Known gaps

These are inconsistencies in the current code, recorded rather than fixed.

1. **Unused Android updater surface.** The page declares `UpdatePlugin.downloadAndInstall` and `UpdateState` (`apps/web/src/native/alarmBridge.ts:213` to `222`) but nothing calls it, and the `updateState` event emitted by `apps/mobile/android-plugin/UpdatePlugin.kt:93` has no page listener. `downloadAndInstall` accepts any `url` without a host or scheme check (`UpdatePlugin.kt:27` to `37`).
2. **Unused `AlarmPlugin` methods.** `schedule` (`alarmBridge.ts:80`) and `canScheduleExactAlarms` (`alarmBridge.ts:96`) have no page caller; they remain native entry points (`AlarmPlugin.kt:122`, `233`).
3. **`close` handling differs.** Windows ignores a `close` within 500 ms of opening (`apps/desktop/Persistent.Desktop/Windows/AppFlyout.xaml.cs:522` to `531`); Linux hides immediately (`apps/linux-desktop/src/main.ts:361` to `363`), so the stale-page protection exists only on Windows.
4. **Unreachable Linux `signedOut` case.** `main.ts:327` handles `signedOut` and returns before the queued switch, so the `case 'signedOut'` at `main.ts:364` never runs.
5. **`pageReady` side effect differs.** Linux sends `hostSettings` on `pageReady` (`main.ts:342` to `344`); Windows does not (`apps/desktop/Persistent.Desktop/Windows/AppFlyout.xaml.cs:538` to `546`). The page re-requests on mount anyway, so the extra send is redundant.
6. **No host version reporting or protocol handshake.** Only Android reports a native version (`apps/web/src/native/clientUsage.ts:37` to `45`); desktop sessions report `nativeVersion: null`, and no message carries a host or bridge version, so the page can only detect capabilities.
7. **Windows does not identify itself in `hostSettings`.** `HostSettings.BuildMessageJsonAsync` sends no `platform` (`apps/desktop/Persistent.Desktop/Classes/Settings/HostSettings.cs:89` to `110`); the page infers Windows from the absence of `window.persistentDesktop` (`desktopBridge.ts:206`).
8. **Linux sends no `deviceTimeFormat`.** `apps/linux-desktop/src/host-settings.ts:28` to `51` omits it, so Match device on Linux uses the regional locale rather than the OS clock setting.
9. **Windows host-to-page posts are not origin-gated.** `PostWebMessageAsJson` calls (`AppFlyout.xaml.cs:322`, `885`, `1034`, `1071`, `1322`) post to whatever top-level document is loaded, which can be `accounts.google.com` because `OnNavigationStarting` keeps that host in the flyout (`AppFlyout.xaml.cs:604`). Linux checks the URL before sending (`hosted-window.ts:418`). The payloads carry no credentials.
10. **Windows external URL handling is broader than Linux.** `OpenExternally` shell-executes any non-app, non-Google URI with no scheme check (`AppFlyout.xaml.cs:659` to `663`), and `IsSignInUrl` matches the host only, not the scheme (`AppFlyout.xaml.cs:654`). Linux allows only `https:` and the exact `https://accounts.google.com` origin (`security.ts:32` to `52`). Windows also opens same-origin popups in the default browser, where Linux opens them in a sandboxed child window (`hosted-window.ts:213`).
11. **Android mirrored cookie is never cleared.** `setSyncConfig` keeps the previously mirrored cookie when the fresh read has none (`AlarmPlugin.kt:172`), and neither `cancelAll` (`AlarmPlugin.kt:217`) nor any other path clears `auth_cookie` (`AlarmStore.kt:46`, `58`). After sign-out the worker keeps presenting the old cookie until the next signed-in `setSyncConfig`; `POST /api/auth/logout` revokes the session (`apps/api/src/routes/auth.ts:187` to `191`), so those requests should fail; an account switch replaces the cookie on the next `syncAlarms()`.
12. **Android link handling is Capacitor's default, set nowhere in this repo.** The `server` block in `apps/mobile/capacitor.config.ts:30` to `33` has no `allowNavigation`, so same-origin links, `target="_blank"` included, stay in the WebView and nothing can send the app's own pages to the system browser (see Other Android plugins and channels).
13. **Windows page-listening flag survives a page self-reload.** `_pageListening` is cleared only in `NavigateToApp` (`AppFlyout.xaml.cs:469`) and set by `pageReady` (`AppFlyout.xaml.cs:541`). When the page reloads itself (for example after a confirmed web build update), the flag stays true, so a `navigate` or `refreshWidgetSnapshot` posted before the new page mounts is sent immediately and can be lost. Linux resets readiness on any new main-document navigation (`apps/linux-desktop/src/page-delivery.ts:14` to `18`).
